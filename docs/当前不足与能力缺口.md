# 当前项目的不足与能力缺口

## 文档目的

本文档用于明确当前仓库的实际能力边界，说明它为什么仍然只是一个基础底座，
以及它距离“AI 驱动的 DeFi 安全 Agent”这一目标还缺少哪些核心能力。

这份文档不是否定当前工作，而是为了避免误判项目成熟度，帮助后续研发有更清晰的优先级和路线。


## 一句话判断

当前项目仍然非常基础。

它更接近于一个“静态扫描脚本 + 示例合约 + 示例报告 + 少量 PoC 验证入口”的研究原型，
而不是一个真正具备自主分析、主动研究、持续审计能力的 AI 驱动 DeFi 安全 Agent。


## 当前已经有的能力

从仓库内容来看，当前项目已经具备以下基础能力：

- 一个 Python 实现的规则型静态扫描器
- 若干启发式分析器，例如访问控制、重入、预言机依赖、算术问题、升级风险
- 一个 Markdown 报告生成器
- 多个协议的示例合约样本
- 若干人工撰写或整理的审计报告
- 一个可运行的 Foundry PoC 测试入口

这些能力说明它已经有了“安全分析工具箱”的雏形，但还远远不足以支撑完整的 Agent 系统。


## 核心不足一：本质上仍是规则型工具，不是 AI Agent

当前项目最根本的问题是，它并不具备真正意义上的 Agent 能力。

### 具体表现

- 没有任务规划能力
- 没有多步骤推理链
- 没有长期记忆或案例记忆机制
- 没有工具编排层
- 没有自主决定下一步分析动作的能力
- 没有针对不同任务动态切换策略的能力

### 结果

当前仓库只能执行“预先写好的分析规则”，而不能像真正的 Agent 一样：

- 先理解目标
- 再拆分任务
- 再调用合适工具
- 再验证假设
- 最后综合生成结论

换句话说，现在更像“扫描器”，不是“智能体”。


## 核心不足二：分析能力仍然停留在启发式和正则规则层

当前的安全分析能力偏浅，很多地方仍然依赖字符串匹配、命名模式和局部启发式判断。

### 具体问题

- 对 Solidity 代码的理解不够语义化
- 缺少完整 AST 级分析
- 缺少控制流分析
- 缺少数据流分析
- 缺少跨函数、跨合约、跨模块的系统级推理
- 缺少调用图、依赖图、权限传播图之类的程序分析结构
- 缺少状态机层面的协议逻辑理解

### 导致的后果

- 容易误报
- 容易漏报
- 很难区分“正常设计”与“真正漏洞”
- 很难识别经济模型类漏洞
- 很难分析复杂协议的交互风险

这意味着当前扫描结果更适合作为“初筛”或“提示”，而不适合作为可靠审计结论。


## 核心不足三：缺少链上数据能力

如果目标是研究历史攻击和审计新上线合约，链上数据能力是核心基础设施，但当前几乎没有建立起来。

### 当前缺失

- 没有链上数据抓取与索引系统
- 没有交易、事件、trace、call graph 的自动化采集能力
- 没有针对历史攻击事件的链上复盘流水线
- 没有对新部署合约的发现机制
- 没有对新市场、新池子、新代理升级的持续跟踪能力

### 直接影响

- 无法系统化分析历史攻击事件
- 无法自动发现值得审计的新目标
- 无法做持续化的链上监控
- 无法把“代码分析”与“真实链上行为”连接起来

没有链上数据层，项目就无法真正进入 DeFi 安全研究的核心场景。


## 核心不足四：缺少历史攻击知识库与案例库

目标之一是“能看之前的攻击事件”，但当前仓库并没有真正意义上的历史攻击案例数据库。

### 当前缺失

- 没有结构化攻击事件库
- 没有事件标签体系
- 没有根因分类体系
- 没有把攻击交易、受害协议、漏洞类别、影响资产统一组织起来
- 没有把历史案例转化成可检索、可比较、可复用的知识

### 结果

即使现在仓库里有一些报告和 PoC，也只是离散材料，不是知识系统。

这样会导致：

- 不能快速对比新协议和历史已知漏洞
- 不能从历史中自动归纳模式
- 不能形成研究型洞察
- 不能支撑后续论文自动生成


## 核心不足五：距离“自动写论文”还有非常大差距

导师提出的目标之一，是系统在有好 idea 的情况下能够自己写出论文。

从当前仓库看，这部分几乎还是空白。

### 当前缺失

- 没有研究问题生成模块
- 没有 novelty 判断机制
- 没有 related work 检索能力
- 没有实验设计框架
- 没有结果组织与图表生成能力
- 没有论文结构化写作流程
- 没有引用管理、文献整合和研究证据管理能力

### 为什么这是大缺口

“写论文”不是把扫描结果改写成学术语气。

它至少需要：

- 提出研究问题
- 说明为什么值得研究
- 说明与已有工作的区别
- 给出方法设计
- 给出实验与验证
- 形成可信结论

当前项目离这一层还很远。


## 核心不足六：距离“自动审计新合约”也还有很大差距

当前虽然能对目标目录里的 Solidity 文件跑扫描器，但这和“自动审计新上线合约”不是一回事。

### 当前缺失

- 没有新合约接入流水线
- 没有自动拉取链上源码与依赖的流程
- 没有代理合约识别和实现合约追踪能力
- 没有协议分类能力
- 没有 TVL、权限、外部依赖、价格源、治理结构等上下文分析能力
- 没有针对不同协议类型切换审计模板的能力
- 没有高风险项自动触发 PoC / fork 验证的机制

### 导致的结果

当前只能说“能扫描一些 Solidity 文件”，不能说“能审计新合约”。

真正的合约审计至少需要：

- 理解目标协议是什么
- 理解它如何交互
- 理解它依赖谁
- 理解它有哪些权限角色
- 理解它的经济约束和攻击面

这些能力当前都不完整。


## 核心不足七：报告生成能力还只是排版层，不是审计写作层

当前仓库里有 Markdown 报告生成器，但本质上更像“结果排版器”，不是“审计报告写作系统”。

### 当前问题

- 报告内容高度依赖已有扫描结果
- 缺少基于证据链的推理组织
- 缺少手工审计常见的上下文说明
- 缺少对业务逻辑、攻击前提、真实利用条件的细化判断
- 缺少不同读者视角下的表达控制，例如工程团队、研究人员、管理层

### 结果

当前能生成的是“格式化结果”，不是高质量审计交付物。

真正高质量的审计报告应当同时具备：

- 技术准确性
- 风险解释能力
- 利用路径分析
- 修复建议的针对性
- 对误报与边界条件的说明

这些方面当前都不够。


## 核心不足八：动态验证能力很弱

当前仓库里虽然有 Foundry PoC 测试入口，但这并不意味着已经具备成熟的动态验证能力。

### 当前问题

- PoC 数量很少
- 缺少统一的验证框架
- 缺少针对不同漏洞类型的标准化验证模板
- 缺少自动从发现项生成测试思路的能力
- 缺少模糊测试、符号执行、状态差分测试等更强的验证手段
- 缺少批量 fork 测试工作流

### 结果

当前动态验证更多还是“个别案例演示”，不是“系统能力”。


## 核心不足九：工程化程度不高

从工程角度看，当前仓库更像研究性质项目，而不是可长期维护的产品或平台。

### 当前问题

- 没有统一的服务架构
- 没有数据库层
- 没有 API 层
- 没有任务队列
- 没有前端或操作界面
- 没有配置管理体系
- 没有日志、监控、指标追踪
- 没有权限控制和多用户协作设计
- 没有稳定的测试体系与 CI 规范

### 直接影响

- 难以扩展
- 难以协作开发
- 难以部署
- 难以复现复杂分析任务
- 难以把研究原型变成真正可用系统


## 核心不足十：评测体系缺失

如果要做 AI 驱动的安全 Agent，必须能回答一个问题：

“它到底做得好不好？”

当前仓库在这一点上几乎没有建立标准。

### 当前缺失

- 没有标准测试集
- 没有历史攻击复现 benchmark
- 没有漏洞检测准确率评估
- 没有误报率 / 漏报率评估
- 没有报告质量评估
- 没有研究输出质量评估
- 没有与人工审计结果的对比机制

### 结果

后续即使加了很多功能，也很难客观判断系统是否真的变强了。


## 核心不足十一：缺少面向 DeFi 的上下文理解层

DeFi 安全和一般智能合约安全的最大区别之一，是它强依赖金融和协议上下文。

当前项目对这部分的建模能力很弱。

### 当前缺失

- 对借贷协议、AMM、稳定币、LST、衍生品等协议类型的专门建模不足
- 对价格形成机制、清算逻辑、会计逻辑、治理流程的理解不足
- 对组合风险、跨协议依赖、流动性来源、预言机路径的理解不足
- 对“代码安全但经济不安全”的问题识别能力不足

### 结果

项目目前更容易发现“代码层面问题”，但难以发现很多真正高价值的 DeFi 风险：

- 经济攻击
- 预言机路径风险
- 设计层脆弱性
- 参数组合导致的利用面


## 核心不足十二：缺少从“发现问题”到“提出研究问题”的桥梁

这是一个非常关键但容易被忽视的差距。

项目未来想做的不只是安全扫描，而是安全研究。

### 当前缺失

- 没有把多个案例抽象成研究问题的机制
- 没有把研究问题转成实验设计的机制
- 没有把实验结果组织成论文论证链条的机制
- 没有从工程发现过渡到研究洞察的中间层

### 结果

即使发现了很多漏洞线索，也很难自动沉淀成“能写论文的 idea”。


## 当前项目更准确的定位

综合来看，当前仓库更准确的定位应当是：

### 它是什么

- 一个 DeFi 安全研究原型仓库
- 一个带有规则型扫描能力的基础工具箱
- 一个可扩展的 PoC / 报告底座

### 它不是什么

- 不是成熟的 AI 安全 Agent
- 不是完整的自动审计平台
- 不是完整的历史攻击研究系统
- 不是论文自动生成系统
- 不是面向生产环境的安全产品


## 最重要的结论

当前项目的最大问题，不是“某个模块写得不够好”，而是整体能力层级还很低。

它已经有了一些有价值的基础材料，但离最终目标仍存在结构性差距：

- 缺 AI Agent 能力
- 缺链上数据能力
- 缺历史攻击知识库
- 缺 DeFi 上下文理解
- 缺动态验证体系
- 缺研究生成能力
- 缺工程化平台能力
- 缺评测标准

因此，后续工作不能只是在现有扫描器上继续加几条规则。

真正需要做的是：围绕最终目标，逐步把这个基础仓库扩展成一个完整的
DeFi 安全研究与审计 Agent 系统。


## 建议的理解方式

对于当前项目，最合理的判断应该是：

- 它适合作为起点
- 它不适合被高估成熟度
- 它目前只是底座，不是成品
- 后续研发重点应当放在“能力层级提升”，而不只是“功能数量增加”
