# AI 驱动 DeFi 安全 Agent 实施路线图

## 1. 文档目标

本文档把系统方案拆成可执行路线图，明确：

- 先做什么
- 后做什么
- 每阶段交付什么
- 如何判断阶段完成

目标不是列一个“愿望清单”，而是把当前基础仓库稳步推进到可交付系统。


## 2. 执行原则

### 原则一：先闭环，再扩展

每个阶段都必须形成可运行闭环，而不是只搭框架。

### 原则二：先证据系统，再智能包装

先把数据、分析、验证、评测打牢，再强化 Agent 表现层。

### 原则三：优先做高价值场景

优先级排序：

1. 新合约审计闭环
2. 历史攻击复盘闭环
3. 研究问题生成
4. 论文草稿生成

### 原则四：每阶段都要有清晰验收

没有验收标准的阶段，不算真正完成。

### 原则五：每一阶段都必须形成“可演示成果”

阶段完成不应只体现在代码数量上，还必须能向导师或评审展示：

- 一个可跑通流程
- 一组可复现结果
- 一份可阅读输出


## 3. 阶段总览

建议拆成 5 个阶段。

- Phase 0：底座整理与工程化补齐
- Phase 1：审计 MVP
- Phase 2：历史攻击研究 MVP
- Phase 3：统一知识库与 Agent 编排
- Phase 4：研究生成与论文工作流


## 3.1 建议阅读顺序

如果后续团队成员只看三份材料，建议阅读顺序是：

1. `docs/项目目标.md`
2. `docs/当前不足与能力缺口.md`
3. 本文档 + `docs/系统方案设计.md`


## 4. Phase 0：底座整理与工程化补齐

## 目标

把当前基础仓库整理成可持续开发的起点。

## 必做事项

- 固定文档位置与工程目录结构
- 明确配置管理方式
- 整理当前扫描器输出格式
- 建立统一的 `Finding`、`Evidence` 数据结构
- 给 Foundry、Python 工具、报告生成器建立基础测试
- 建立最基础的 CI

## 推荐交付物

- 稳定的目录结构
- 文档索引
- 基础 CI 流程
- 统一 schema 定义
- 一组最小回归测试

## 验收标准

- 新成员可以在本地跑通全部基础工具
- 扫描结果有统一 JSON schema
- 测试与 CI 能覆盖最关键路径
- 文档结构和工程结构不再继续失控扩散


## 5. Phase 1：审计 MVP

## 目标

先把“新合约审计”做成最小可用闭环。

## 核心能力

- 接收目标合约或协议地址
- 拉取源码与依赖
- 做协议分类与基础上下文识别
- 运行静态分析
- 检索相似历史漏洞
- 汇总证据
- 生成结构化审计报告

## 推荐模块

- `contract_ingestion`
- `protocol_classifier`
- `static_analysis_pipeline`
- `evidence_aggregator`
- `audit_report_writer`

## 本阶段不要过度做的事

- 不要急着做复杂多 Agent
- 不要先做论文自动生成
- 不要一开始就覆盖所有 DeFi 协议类型

## 优先支持的协议类型

- 借贷
- Vault / share-based 协议
- AMM

## 验收标准

- 能对一个新目标协议输出完整审计报告
- 报告中每个高风险结论都有证据支撑
- 至少能对部分高风险问题触发 PoC 或 fork 验证
- 人工评审后，报告达到“可以作为初稿继续精修”的质量

## 阶段演示建议

- 输入一个协议地址或源码目录
- 自动完成接入、分析、相似案例检索与报告生成
- 展示至少一个高风险 finding 的证据链和验证结果


## 6. Phase 2：历史攻击研究 MVP

## 目标

把“能看之前的攻击事件”做成真正可复用的系统能力，而不是手工整理笔记。

## 核心能力

- 导入历史攻击案例
- 存储攻击交易、受害协议、根因、攻击路径
- 自动生成案例摘要
- 自动归纳漏洞模式
- 支持相似案例检索

## 推荐模块

- `incident_ingestion`
- `attack_trace_parser`
- `incident_knowledge_base`
- `pattern_extractor`
- `incident_report_writer`

## 验收标准

- 至少沉淀一批高质量结构化攻击案例
- 新审计任务能调用历史案例库
- 系统能回答“这个风险像哪些历史攻击”

## 阶段演示建议

- 选择 3 到 5 个典型历史攻击
- 展示系统如何自动重建攻击摘要、根因、模式标签和相似案例关系


## 7. Phase 3：统一知识库与 Agent 编排

## 目标

把审计与研究两条线整合起来，形成真正的 Agent 工作流系统。

## 核心能力

- 统一任务入口
- 统一证据模型
- 统一案例库和报告库
- 统一工具编排
- 统一结果追踪

## 推荐模块

- `task_orchestrator`
- `tool_registry`
- `memory_store`
- `retrieval_service`
- `experiment_manager`

## 核心里程碑

- 输入一个目标协议，系统能自主决定：
  先做哪些分析、调哪些工具、什么时候触发验证、什么时候检索历史案例

## 验收标准

- 工作流可复现
- 工具调用有日志
- 结论可追溯到证据对象
- 审计与研究不再是两套割裂流程

## 阶段演示建议

- 给系统一个目标任务
- 演示系统如何决定调用哪些分析模块、是否触发验证、何时检索历史案例
- 展示完整任务状态流转


## 8. Phase 4：研究生成与论文工作流

## 目标

把系统从“安全分析系统”提升到“能辅助研究和论文输出的研究型 Agent”。

## 核心能力

- 从案例与发现中抽象研究问题
- 识别潜在 novelty
- 组织 related work
- 设计实验计划
- 汇总实验结果
- 生成论文草稿

## 推荐模块

- `research_question_generator`
- `related_work_retriever`
- `experiment_planner`
- `paper_outline_builder`
- `paper_draft_writer`

## 验收标准

- 能从多个案例中提出有意义的研究问题
- 能生成结构化研究备忘录
- 能输出一篇具备学术论文基本结构的初稿

## 阶段演示建议

- 从多个案例自动归纳一个研究问题
- 生成研究备忘录
- 生成一版论文结构草稿


## 9. MVP、v1、研究版的边界

## MVP

定义：

一个能完成“新合约审计闭环”的最小系统。

必须具备：

- 合约接入
- 基础协议分类
- 静态分析
- 相似案例检索
- 审计报告生成

可以暂时不具备：

- 论文生成
- 复杂图分析
- 高级多 Agent


## v1

定义：

一个同时具备“新合约审计闭环 + 历史攻击复盘闭环”的系统。

必须具备：

- 结构化历史案例库
- 审计与历史案例联动
- 高风险项验证能力
- 统一证据模型


## 研究版

定义：

一个能够从案例和审计发现中生成研究问题，并支持论文型输出的系统。

必须具备：

- 研究问题生成
- 实验设计与归档
- 论文草稿生成
- 研究成果评审闭环


## 10. 技术优先级建议

如果资源有限，建议按下面的顺序推进。

### P0

- 统一 schema
- 合约接入
- 静态分析升级
- 报告生成升级
- 基础 CI 与测试

### P1

- 历史攻击案例库
- 相似案例检索
- PoC / fork 验证工作流
- 协议分类

### P2

- Agent 编排
- 研究问题生成
- 论文草稿系统
- 更复杂的图分析与大规模索引


## 10.1 建议的 12 周落地节奏

这个节奏不是唯一解，但适合作为第一轮执行参考。

### 第 1-2 周

- 固定目录结构
- 补齐 schema
- 清理基础工具接口
- 建立 CI 和最小测试

### 第 3-4 周

- 完成合约接入模块
- 输出统一 Finding / Evidence
- 初步升级报告生成器

### 第 5-6 周

- 加入协议分类
- 加入相似历史案例检索
- 建立审计 MVP 闭环

### 第 7-8 周

- 建立历史攻击案例库
- 完成攻击案例导入与摘要生成
- 打通审计与案例联动

### 第 9-10 周

- 建立任务编排层
- 接入验证调度
- 补齐任务状态机与日志

### 第 11-12 周

- 做一次完整演示版
- 补 benchmark
- 形成导师可评审的中期交付


## 11. 评测体系路线图

## 阶段一：功能可用性评测

- 能否跑通
- 能否生成输出
- 输出格式是否稳定

## 阶段二：分析质量评测

- 漏洞识别准确率
- 误报率
- 漏报率
- 历史案例匹配效果

## 阶段三：验证有效性评测

- PoC 成功率
- fork 测试成功率
- 假设验证闭环率

## 阶段四：结果质量评测

- 审计报告质量
- 历史攻击复盘质量
- 研究问题质量
- 论文草稿质量


## 12. 主要风险与应对

## 风险一：基础分析层不稳，导致上层 Agent 全部失真

应对：

- 先补底层分析和证据模型
- 上层推理必须绑定证据

## 风险二：过度追求 Agent 形态，忽视实际闭环

应对：

- 每阶段必须定义输入、处理、输出、验证

## 风险三：系统越做越大，但没有 benchmark

应对：

- 早期就建立测试集和对照集

## 风险四：只积累资料，不沉淀结构化知识

应对：

- 所有案例、报告、实验都必须进统一数据模型

## 风险五：过早做论文生成，反而拖垮底层建设

应对：

- 先把审计闭环和案例库做扎实
- 论文工作流放到 Phase 4 再系统推进


## 13. 当前建议的下一步

如果从今天开始推进，最合理的顺序是：

1. 完成 Phase 0 的工程整理与 schema 统一
2. 直接启动 Phase 1，先做审计 MVP
3. 在审计 MVP 基础上补历史攻击案例库
4. 再做 Agent 编排与研究工作流

原因很直接：

- 审计闭环最接近当前底座
- 历史攻击研究可以复用审计基础设施
- 论文工作流必须建立在前两者之上


## 13.1 如果只能做一件事

如果时间极度有限，只能优先做一条主线，那么应优先做：

“新合约审计 MVP”

原因：

- 最贴近当前仓库已有底座
- 更容易形成可演示闭环
- 对后续历史攻击研究与论文工作流都有复用价值


## 14. 结论

最优实施路线不是“同时做所有事情”，而是：

先把基础仓库升级成一个能稳定完成新合约审计的系统，
再把历史攻击研究能力接进去，
最后再把研究问题生成与论文工作流搭起来。

这样推进，既符合当前项目基础，也最有机会把系统真正做成，而不是一直停留在概念层。
